# 팀 8 평가기

교차평가용 채점기. 골드셋과 팀별 답변 파일을 받아 총점(0~100)을 매기고
`eval_8.json` 을 만든다.

| 파일 | 무엇 |
|---|---|
| [평가기_팀8.ipynb](평가기_팀8.ipynb) | **제출물.** 새 Colab에서 위에서 아래로 한 번 실행 |
| [evaluator_core.py](evaluator_core.py) | 채점 로직 원본. 노트북 셀은 이 파일을 쪼갠 것 |
| [build_notebook.py](build_notebook.py) | 코어를 고친 뒤 노트북을 다시 만드는 스크립트 |
| [test_evaluator.py](test_evaluator.py) | 로컬 검증 88건 |
| [eval_8.json](eval_8.json) | 규칙 기반 판정 + 공개 4팀 답변으로 돌려 본 예행 결과 — **운영진 검사기를 통과하는 형식이 아님**, 아래 "산출물" 참고 |

```bash
python3 test_evaluator.py     # 검증 (88건, Gemini 배선은 가짜 SDK로 모킹)

```

## 채점식

```
총점 = 0.20 × (MRR × 100) + 0.30 × (키팩트 F1 × 100) + 0.50 × (판정 0~100)
판정 = 10 × (0.40·정확 + 0.25·근거 + 0.20·완결 + 0.15·명료)      각 축 0~10
```

가중치와 지표 정의는 처음에 공식 채점 결과(`practice_result_8/12/13.json`)에서
역산했고, 이후 운영진이 직접 확인해 준 배점(MRR 20 · 키팩트 30 · LLM판정 50,
축 이름 정확성·근거성·완결성·명료성)과 정확히 일치했다.

## 판정 축 실채점 — Gemini 3.5 Flash (운영진 필수 요구사항)

운영진 지침: **"Gemini 3.5 Flash로 공개 10문항과 비공개 30문항을 같은 코드로
처리하고, 익명 5팀 모두에 같은 기준을 적용해야 합니다."**

`evaluator_core.make_gemini_judge(api_key)` 가 이 요구를 만족하는 `judge_fn` 을
만든다. 노트북 5b·9·10절이 이걸 쓴다.

- **모델 고정** `gemini-3.5-flash`, SDK는 `google-genai`. 문항당 API 호출 1회로
  4축을 한 번에 JSON으로 받는다(`response_mime_type=application/json` + 스키마).
- **temperature=0** — "같은 기준을 같은 코드로 5팀에" 요구에 맞춰 변동을 최소화.
- **재시도 3회 후 폴백** — 네트워크 오류·429·JSON 파싱 실패가 반복되면 **그 문항
  하나만** 5절의 규칙 기반 심판으로 대체하고 사유에 남긴다. 한 문항의 일시적
  실패로 나머지 문항·다른 팀 채점까지 멈추지 않기 위함이다.
- **`stats`로 투명하게** — `{"calls","gemini_ok","fallback"}` 을 실시간 집계한다.
  `fallback > 0` 인 채점 결과는 "Gemini로 처리"를 만족하지 못하므로, 노트북
  10절 실행 후 이 값을 확인하고 크면 키·쿼터를 점검해 다시 돌려야 한다.
- **속도 제한** 성공 호출마다 4.5초 대기(무료 등급 분당 요청 수 방어, 조정 가능).
  5팀 × 30문항 기준 대략 10~20분 걸린다.

`generate_content`(문서상 "레거시")를 택했다 — 신설 Interactions API(2026-06 GA)보다
구조화 출력 문서·사례가 안정적이어서다. 정확한 API 표면은 실행 시점에 바뀔 수
있으므로, 노트북 9절에 **1문항 스모크 테스트**를 넣어 200문항 가까운 실채점 전에
싸게 검증하도록 했다.

## 지표

**MRR** — `retrieved` 를 앞에서부터 훑어 정답 조항이 처음 나온 순위의 역수.
`gold_articles` 가 여러 개면 그중 하나만 맞아도 정답으로 본다.

**키팩트 F1** — 답변 전체를 토큰 **집합**으로 보고 `key_facts` 전체와 F1.
문장 단위가 아닌 통짜 비교라 **빠뜨려도 깎이고 덧붙여도 깎인다.**
토큰은 `re.findall(r"\w+", NFKC(text))`. 공식 점수를 기약분수로 분해해
공개 10문항 전부에서 이 정의와 앞뒤가 맞는 것을 확인했다.

**판정 4축** — 실채점은 위 Gemini 3.5 Flash가 한다. 아래 규칙 기반 버전
(`judge_rule_based`)은 **자체 검증(8절, API 키 불필요)과 Gemini 실패 시 문항 단위
폴백 전용**이다 — 같은 입력에 항상 같은 점수를 내는 결정론이 두 용도에 맞아서다.

| 축 | 깎는 조건 |
|---|---|
| 정확 accuracy | 단위는 같은데 숫자가 다름(`6개월`→`3개월`), 명시적 예/아니오 뒤집힘, 정답과 거의 안 겹침 |
| 근거 grounding | 정답 조항 순위 (1위 10 → 2위 8 → 3위 7 → 4위↓ 6 → 없음 2), 근거 미제시 0 |
| 완결 completeness | 팩트별 토큰 겹침 40% 미만이면 누락. `10 × 반영비율^0.4` |
| 명료 clarity | 정답 길이의 4배 초과, 같은 말 과도 반복 |

## 규칙 기반 폴백의 보정 근거

폴백이 아무렇게나 깎아서는 안 되므로(0점보다는 나아야 하는 대체값), 공식 심판이
매긴 축 점수 30건(3팀 × 공개 10문항)에 맞춰 정했다. 그 30건에서 나온 사실이
설계를 결정했다.

- 감점이 **completeness에 쏠려 있다** (16회 중 10회). 팀을 가르는 축은 사실상 여기다.
- accuracy·grounding·clarity는 거의 만점이다. 이 축에서 길이나 부정어 같은 얕은
  신호로 깎았더니 공식 점수와의 상관이 **음수**가 됐다 — 부정어 규칙은 발동한 4건이
  전부 오탐이었다. 그래서 확실한 증거가 있을 때만 깎도록 좁혔다.

결과: 공식 심판과의 상관 **r = 0.19 → 0.72**, 규칙 기반만으로 계산한 팀 총점도
공식 대비 1점 안쪽 재현(아래 표). Gemini를 못 쓰는 상황(폴백)에서도 등급 없는
0점보다 훨씬 신뢰할 수 있는 대체값이라는 뜻이다.

| 팀 | 규칙 기반 평가기 | 공식 | 차 |
|---|---|---|---|
| 8 | 87.70 | 87.50 | +0.20 |
| 12 | 89.46 | 88.80 | +0.67 |
| 13 | 88.15 | 87.14 | +1.01 |

로컬 답변 파일이 실제 채점된 실행과 같은 회차가 아니라(키팩트 F1이 최대 0.026 차이,
총점 0.8점어치) 이 표의 차이에는 회차 차이가 섞여 있다. 팀 간 0.36점 차를 가르는
수준의 순위 검증은 이 데이터로는 불가능하다.

## 트랩 문항에서 F1이 못 보는 것

공개 P08은 "본 약관이 세부지침보다 우선하나요?"에 정답이 "아니오"인 함정 문항이다.
어떤 팀 답변은 정답 조문을 **그대로 인용하면서 결론만 반대로** 냈다.

- 키팩트 F1 0.565 — 원문을 인용했으므로 토큰은 겹친다. **못 잡는다.**
- 규칙 기반 정확 축 6.0 — "정답은 '아니오'인데 '예'로 답함". **잡는다.**

토큰 겹침만으로는 결론이 뒤집힌 답변을 거를 수 없다는 뜻이고, 판정 축(실채점은
Gemini, 폴백은 규칙 기반)을 F1과 별도로 두는 이유이기도 하다. Gemini는 의미를
읽는 심판이므로 이런 트랩을 규칙 기반보다 더 안정적으로 잡을 것으로 기대하지만,
이건 실제 API 호출로 확인해야 할 부분이지 이 문서가 검증한 사실은 아니다.

## 입력 계약

골드셋에서 읽는 필드는 넷뿐이다.

- `questions[].id` — 답변 파일의 `qid` 와 연결
- `questions[].question`
- `questions[].gold_articles[].{doc, article, citation}`
- `questions[].key_facts`

`ptype`·`difficulty`·`_meta` 같은 추가 필드는 **있어도 쓰지 않고 없어도 돈다.**
문항 id와 문항 수도 코드에 박지 않고 전부 입력 파일에서 읽는다. 검증 셀이
`B001`~`B030` 이라는 다른 id 체계·다른 문항 수의 가짜 골드셋으로 돌려 이를 확인한다.

**정상 입력은 결과기가 만든 `answers_public_<팀>.json` 을 그대로 쓰면 된다** —
`qid` 는 원래 골드셋의 `id`(`P01`~`P10` 등)와 같다. 다만 `qid` 가 골드셋 id와
전혀 다른 라벨(예: `BLIND01`)을 쓰는 입력이 들어와도, 개수가 같으면 제출 순서를
골드셋 순서에 그대로 대응시켜 살린다(`_resolve_qid_mapping`, §6) — 평가기가
흉내 낼 입력 형태가 아니라 **예외 상황에서도 죽지 않기 위한 방어**다.

표기 흔들림은 흡수한다. 조번호는 `10` / `"10"` / `"제10조"` / `"제 10 조"` 를 모두
같게 읽고, 문서명은 공백을 지우고 비교한다
(`카카오 통합서비스약관` 과 `카카오 통합 약관` 은 공백을 지워도 달라 안전하다).

## 깨진 파일 처리 — status는 항상 `completed`

운영진이 배포한 "교차 평가 결과 파일 검사기"로 알게 된 규칙: **BLIND01~BLIND05 중
하나라도 `status != completed` 면 내 제출 파일 전체가 순위 산정에서 제외된다.**

> "일부 문항 실패·평가 전체 실패·후보 중복·누락이 하나라도 있으면 그 평가 결과 파일
> 전체가 순위 산정에서 제외됩니다. 실패한 후보에게 0점을 주는 방식은 사용하지
> 않습니다."

즉 한 후보의 답변 파일이 아무리 깨져 있어도 `partial`/`failed` 로 도망치면 **그
후보만 감점되는 게 아니라 내 제출 전체가 무효화**된다. 그래서 `evaluate_submissions`
는 파일을 전혀 못 읽어도 빈 답변(`{}`)으로 채점을 강행해 실제 점수(대개 0점에 가까움)
를 매기고 `completed` 로 마감한다 — `load_answers`/`evaluate_team` 이 이미 빈 입력을
정상적인 0점 만점 채점으로 처리하도록 설계돼 있어 가능하다. 채점 중 있었던 문제는
제출 파일이 아니라 `details[blind_id]["problems"]` 에만 남는다(진단용).

`blind_id` 는 파일 안 `blind_id` → **파일명(basename)** 의 `BLIND\d+`(숫자는 항상
2자리로 정규화) → 파일명 나머지 → `team` → 순번 순으로 정한다. 경로 전체가 아니라
파일명만 보는 이유: 상위 폴더 이름에 숫자가 섞이면(`blind5/answers_BLIND01.json`
같은 구조) 전체 경로를 보는 정규식이 폴더명의 숫자를 먼저 집어 모든 파일이 같은
`blind_id`로 뭉개지는 사고가 실제로 있었다(이 프로젝트 검증 중 발견, 회귀 테스트로
고정해 둠).

`check_blind_id_coverage(results)` 는 제출 직전 `BLIND01`~`BLIND05` 가 정확히 한
번씩만 있는지 확인한다(중복·누락·이물질). 노트북 10절이 `eval_8.json` 을 쓰기 전에
자동으로 이 검사를 돌려, 문제가 있으면 파일을 만들지 않고 바로 멈춘다.

## 제출 파일 형식 검사

`validate_eval_document`/`check_eval_file`(§7b)은 운영진이 배포한 "[학생용] 교차
평가 결과 파일 검사기"를 그대로 옮긴 것이다 — 재구현하지 않은 이유는 조건 하나라도
다르게 해석하면 "내 검사는 통과했는데 실제 제출은 반려"되는 상황이 생기기 때문이다.
확인하는 것: `schema_version`/`rank` 금지, 결과가 정확히 5개(BLIND01~05, 중복·누락
없음), `status` 전부 `completed`, `total` 이 0~100 범위(단 `failed`면 `null`),
파일명이 `eval_1.json`~`eval_17.json` 형식. 노트북 10절은 `eval_8.json` 을 저장하자마자
이 검사를 자동으로 돌려 `[제출 가능]`/`[확인 필요]` 를 바로 보여 준다.

## 산출물

```json
{"results": [{"blind_id": "BLIND01", "total": 72.3147, "status": "completed"}]}
```

저장소의 [eval_8.json](eval_8.json)은 **규칙 기반 심판**(5절, Gemini API 키 없이도
파이프라인 구조를 보여 주려고)으로 더미 답변 파일 5개를 돌려 본 예행 결과다.
`BLIND01`~`BLIND05` 5개, `check_eval_file` 로 검사하면 `[제출 가능]` 이 뜬다.

더미 5개는 이렇게 만들었다 — **결과기 정상 출력을 손대지 않는 게 원칙**이다.

- `BLIND02`~`BLIND04`: 실제 팀들의 `answers_public_<팀>.json` 을 **그대로**
  복사했다(`qid` 는 원래대로 `P01`~`P10`). 개발·연습 단계 입력은 결과기가 만든
  파일 그대로 쓰면 된다는 원칙을 지켰다.
- `BLIND01`: 운영진이 준 예시 파일 — `qid` 가 `P01`~`P10` 이 아니라 `BLIND01`~
  `BLIND10` 이었다. 골드셋 id 와 하나도 안 겹치지만 개수(10개)는 같아서
  `_resolve_qid_mapping()` 의 위치 기반 폴백이 켜졌고(§6), 92.29점으로 정상
  채점됐다 — 문자열 매칭만 했다면 이 파일은 전부 0점 처리됐을 것이다.
- `BLIND05`: 일부러 `P01`~`P03` 세 문항만 응답한 불완전한 제출. 개수가 안 맞아
  폴백은 켜지지 않고(안전하게 짜맞추지 않음), 응답한 3문항만 정상 채점돼
  7.97점 — `status` 는 여전히 `completed` 다(§7 계약대로).

이 예행 결과는 **연습용**이다. 이 안내(대회 정보 3번째 안내)가 확정한 것: 개발·연습
단계는 `결과기`가 만든 공개 10문항 답변 파일을 그대로 쓰면 되고, `qid` 를 손댈
필요가 없다 — `BLIND01`처럼 다른 라벨을 쓰는 입력은 예외 상황이고, 그런 입력이
와도 죽지 않게 만드는 게 평가기의 일이지 평가기가 흉내 낼 입력 형태는 아니다.
3일차 실제 채점 입력은 **본선 5팀의 비공개 30문항 익명 답변 파일**이다 — 공개
10문항이 아니라 비공개 30문항, 팀 이름이 아니라 익명 5팀이라는 두 가지가 다르다.

본선에 제출할 `eval_<팀>.json`은 노트북 9절(API 키 + 스모크 테스트)과 10절(실행,
`judge_fn=gemini_judge`)을 실제 Gemini API 키로, **익명 5팀의 비공개 30문항 답변
파일 정확히 5개**로 돌려 새로 만든다. 10절 실행 후 확인할 것 두 가지:
