## 1. 청킹 (Chunking)

- 항(①②③, 1.2.3.) 단위 서브청크를 별도로 만들어 **검색 스코어링에만** 사용(BM25 RRF 결합,

- `•`(글머리기호) 분할 추가를 리뷰 피드백으로 검토 → 실측 결과 20문항 MRR 0.9457→0.9239로
  **악화**, 기각. 원인: 분할이 세밀해질수록 보일러플레이트 중복 문서의 짧은 항목이 `max()`
  집계에서 우연히 튀는 위험이 커짐.
- RRF k값(5/10/60), 서브청크 집계 방식(max/mean/top2sum) 스윕 → **max, k 무관**이 최선으로
  확인(기존 설계 그대로 유지가 정답).

## 2. 검색 (Retrieval)

### 2-1. 기각한 아이디어
- **dense(임베딩) 검색 추가**: 단독 성능이 BM25보다 낮고(공개 0.90/함정 0.80 vs 1.00/0.95),
  RRF 3번째 채널로 추가해도 이미 맞던 문항을 끌어내림(공개 10문항 1.00→0.95). 기각.
- **전수 리랭킹**(BM25 생략, 서브청크 343개 전부 리랭킹): CPU 기준 질문당 24.45초 — 검토
  중단(F1 진단으로 우선순위 이동, 결론 못 냄).

### 2-2. 실제로 고친 버그
- **리랭커 512토큰/1000자 truncation**: 72개 조항 중 8개(11%)가 실제로 뒷부분 유실. 최악
  사례(통합서비스약관 제12조, 금지행위 12~23번)는 리랭커가 관련 점수를 0.03으로 오판(정답
  스코어 0.85 대비). truncation 제거 + `max_length` 512→2048로 20문항 MRR 0.9500→0.9750
  개선(T09 회복), 속도도 로컬에서 오히려 개선.
- **이중 sigmoid 버그**: `CrossEncoder.predict()`가 이미 `activation_fct=Sigmoid`로 0~1
  확률을 반환하는데, 기존 코드가 그 위에 `_sigmoid()`를 한 번 더 씌워 모든 점수를
  0.70~0.73 구간으로 압축시키고 있었다. 제거 후 정답/오답 점수 차가 복원됨(정답 1.000 vs
  "6개월 이상" 오답 0.986).
- **컷오프를 비율(ratio)→절대 점수차(margin)로 전환**: 점수가 1.0 근처에 몰려 있으면 비율
  컷오프가 관대해짐(0.986도 0.7배보다 큼). P02(정답3+무관1)·P05(정답1+위험1)·P08(정답1+
  위험2)로 실측해 `margin=0.01`이 세 경우 모두 골드 개수와 정확히 일치함을 확인.
- **`_ARTICLES_JSON_FALLBACK` 미정의 버그**: 세션 초반 발견(GitHub 다운로드 실패 시
  `NameError`로 결과기 전체가 죽음). 이후 "다른 팀 코드"로 통째 교체하며 원천 해결(문자열
  리터럴 내장, 다운로드 자체가 없음).

### 2-3. "다른 팀 코드"와의 비교·병합
- 사용자가 다른 팀(또는 다른 구성원)이 작성한 별도 구현체를 제시 → 4개 축(청킹/검색/
  전처리후처리/생성)으로 상세 비교.
  - 그쪽 특징: 원문 내장 리터럴(다운로드 없음, 더 안전), 문서명 명시 시 후보 풀 하드
    필터링, `_best_subchunk_for_question`(리랭커에 조 전체 대신 질문과 가장 가까운 항만
    전달), `dominance_gap` 컷오프, 질문 분해(`_decompose_question`), 이진 판정을
    log-probability로 검증(`_infer_binary_conclusion`), 구조 검증 후 재생성(retry).
- **실측 비교**(20문항, 실제 리랭커): 우리 단독(margin=0.01) MRR 0.9750(T01 실패) vs 그쪽
  단독(dominance_gap) MRR 0.9750(T03 실패) — **점수는 동률, 실패 지점이 정반대**.
- **리랭커 2채널 RRF 결합**(조 전체 리랭킹 순위 + 서브청크 리랭킹 순위를 RRF로 결합, BM25
  때와 같은 원리): 20문항 전부 1위, **MRR 1.0000** 달성. T01·T03·T09 전부 해결.
  실제 리랭커로 검증 완료(로그 확보).
- 사용자가 이 "다른 팀 코드" 파일 전체로 우리 노트북을 **통째 교체**하기로 결정 → 실행.
  스트레이 셀(중복된 GPU 메모리 체크 조각) 1개 제거해 대회 규격(2셀) 복원.
- 교체 후 베이스에 **리랭커 2채널 RRF 결합을 다시 이식**(`rerank_margin=0.01`,
  `dominance_gap`/`rel_gap_ratio` 방식 대체) — 문서명 필터링 등 그쪽의 다른 기능은 그대로
  보존. **이 최종 조합에 대한 20문항 전체 재검증은 세션 종료로 미완료** — 다음에 반드시
  재실행 필요.

## 3. 전처리/후처리 (`_postprocess_answer`)

- 인용 표기 버그가 매 제출마다 다른 변형으로 재발(문서명 리터럴 → `제②조` → `제4조 제1항
  7호` → `[근거1]` → `(근거1 참조)` → `제N조와/에서` ...) — 순수 열거 방식의 한계를 반복 확인.
- **구조적 일반화**: 개별 연결어 나열 대신 "근거지시명사(조/항/규정/조항/약관/조문) + 조사"
  라는 문법 구조 자체를 정규식으로 포착 → 한 번도 테스트 대상으로 안 넣은 신규 변형 5종
  ("해당 조항에 따라", "관련 규정을 보면" 등) 전부 커버 확인. "법/법률" 뒤는 예외 처리해
  법령 인용(P05) 보존.
- 요약 접속사(따라서/그러므로/...) 목록을 8종까지 확장, **문장 전체 삭제 → 접속사 단어만
  삭제**로 변경(문장째 지우면 접속사 뒤에 진짜 정답이 있을 때 같이 사라지는 위험을 리뷰
  피드백으로 발견 → 실측 시나리오로 검증 후 수정).

## 4. 생성 (System Prompt)

- 세션 시작 시 `_SYSTEM_PROMPT`가 비어 있던 상태에서 12규칙으로 재작성(key_facts를 원문과
  대조해 "정답 단위=문장"이라는 원칙 확립, F1 시뮬레이터로 "문장 통째 복사"가 최적임을 실측).
- 예/아니오 판정어를 문장 앞→뒤로 이동(F1 손해 없음을 bag-of-tokens 특성으로 확인), "예외를
  찾아 뒤집어라"던 규칙 삭제(P09 회귀 유력 원인).
- **실제 공식 채점 데이터**(`practice_result_8.json`)로 F1 낮은 문항(P08 0.195, P09 0.212)을
  정밀 진단 → "질문이 문자 그대로 안 물은 인접 문장도 key_fact가 요구" 패턴 발견 → 규칙
  11·12(근거 조항의 범위: 짧으면 통째로, 길면 같은 화제만) 신설.
- **과적합 감사**(사용자 요청)로 발견/수정: 규칙 12 예시 문구가 P09 실제 내용을 그대로
  담고 있어 가상 사례로 교체, `max_new_tokens` 640(P03 하나만 보고 정함)→2200(72개 조항
  전수의 실제 최장 조항 2173토큰 기준 재계산), `_REF_NOUN` 동의어 소폭 확장.
