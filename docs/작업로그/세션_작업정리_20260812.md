# 작업 정리 — 2026-08-12 세션

이 세션에서 진행한 **7B 양자화 적용(코드 수정)** 과 **검색 컷오프 분석(조사만, 코드 미수정)** 을 정리한다.
관련 코드: [`결과기_팀구현.ipynb`](결과기_팀구현.ipynb). 백업본: `scratchpad/결과기_팀구현.bak.ipynb`(이 세션 패치 직전 상태).

> **주의**: 이 세션 시작 시점의 `결과기_팀구현.ipynb`는 생성 모델이 `Qwen2.5-3B-Instruct` fp16이었다.
> (전날 세션들이 만든 `USE_7B_GENERATION` 스위치 방식과는 다른 상태 — 그 스위치 흔적이 없는 파일에서 출발했다.)
> 아래 7B 패치는 그 3B fp16 버전 위에 얹었다. 여러 편집 흐름이 병행 중이므로 최종 제출본을 정할 때 파일 대조가 필요하다.

---

## 요약 (TL;DR)

1. **7B 양자화 적용 — 파일 수정 완료.** 생성 모델을 3B fp16 → 7B NF4 4bit로 바꾸고, 실패 시 3B 자동 폴백 + 타임아웃 방어 가드를 넣었다. 문법·로딩 분기는 검증했으나 **실제 T4 GPU 검증은 못 함**(로컬에 GPU 없음).
2. **검색 컷오프 분석 — 조사만, 코드 미수정.** 사용자가 붙인 검색 하네스 표(P02 recall 실패)를 조사. 현재 컷오프가 리랭커 확신도가 아니라 RRF 순위 계단만 반영하는 구조임을 실측으로 규명하고 대안(원점수 임계값)을 검증했다. **어떤 코드도 바꾸지 않았다.**

## 1. 7B 양자화 적용 (코드 수정)

### 배경
사용자 요청: "현재 3B로 하고 있는데 7B 양자화를 적용하는 방법."

대회 제약(PDF p8, `[학생용]_결과기_개발_기본_틀.ipynb`)을 먼저 확인:
- 생성 모델 계열은 `Qwen2.5-Instruct`로 **고정**, 단 "정확한 모델 크기와 로딩 옵션은 자유" → 7B 4bit 합법.
- 실행 환경 Colab T4(15GB), **torch 재설치 금지**, 새 세션에서 위→아래 1회 실행(실패 시 0점).
- 러너 문항당 타임아웃 **120초**(`_SP_PER_Q_TIMEOUT_S = 120`, 2번 셀).

### 메모리 계산 (왜 양자화가 필수인가)
| 구성 | VRAM |
|---|---|
| 7B fp16 (양자화 없이) | 15.2 GB → **T4 OOM 확정** |
| 7B NF4 4bit | ~5.6 GB |
| 리랭커 bge-reranker-v2-m3 fp16 | ~1.2 GB |
| KV 캐시(4k 토큰) | ~0.25 GB |
| **합계** | **~7 GB / 15 GB** ✅ |

메모리는 여유. **실제 리스크는 120초 타임아웃**(7B 4bit는 3B보다 토큰당 2~3배 느림).

### 적용한 변경 — [`결과기_팀구현.ipynb`](결과기_팀구현.ipynb) 1번 셀 4곳

1. **bitsandbytes 조건부 설치** (~라인 40, 64)
   - `_pip_install_no_deps()` 헬퍼 추가 → `--no-deps`로 설치해 **torch 재설치(=0점) 원천 차단**.
   - CUDA일 때만 설치하고 `try/except`로 감쌈. 실패 시 `_HAS_BNB = False`로 넘어가 셀이 죽지 않음.

2. **7B NF4 4bit 로딩 + 3B 폴백** (~라인 999~1093)
   - `GEN_MODEL_NAME = "Qwen/Qwen2.5-7B-Instruct"`, `GEN_FALLBACK_MODEL_NAME = "Qwen/Qwen2.5-3B-Instruct"`.
   - `BitsAndBytesConfig(load_in_4bit, nf4, double_quant, compute_dtype=float16)`.
     - **`compute_dtype`은 반드시 fp16** — T4(sm_75)에는 bf16 텐서코어가 없다.
   - `_load_fallback_model(reason)` 헬퍼로 3B 폴백 경로를 단일화. 리랭커와 같은 폴백 구조(로딩 실패가 곧 0점이므로).

3. **재시도 생성 시간 예산 가드** (~라인 1018, 1926)
   - `RETRY_DEADLINE_S = 45.0`. 문항 시작 시각 `_q_t0` 기록 후, 45초 초과 시 구조 재시도(`_generate` 2회차) 생략.
   - 목록형 질문(최대 512토큰) + 재시도가 겹치면 7B 4bit 속도로 120초를 넘길 수 있어서.

4. **GPU 메모리 로그** (~라인 1079) — 로딩 직후 실제 점유량 출력.

`_MODEL`/`_TOKENIZER` 변수명을 그대로 유지 → `_generate`, `_candidate_completion_mean_logprob` 등 나머지 코드는 무수정.

### 검증한 것 / 못 한 것
- ✅ 두 셀 Python 문법 통과.
- ✅ 로딩 분기 **5가지**를 가짜 로더(fake loader)로 실행 — GPU 없음 / bnb 사용 불가 / 4bit 성공 / 4bit OOM / `BitsAndBytesConfig` import 실패 → 모두 의도한 모델로 라우팅(전체 PASS).
- ❌ **실제 T4에서 4bit 로딩 성공 여부와 문항당 지연시간은 검증 못 함**(로컬 GPU 없음). Colab에서 확인 필요.

### Colab에서 확인할 것
1. 로딩 로그가 `... Qwen2.5-7B-Instruct (NF4 4bit) ... → 준비 완료 — Qwen2.5-7B-Instruct`로 끝나는지. `3B-Instruct`로 끝나면 폴백이 탄 것(바로 위 경고 줄에 이유).
2. `[GPU 메모리] allocated`가 7GB 안팎인지, 목록형 문항(P03·P05)이 **90초 이내**인지. 100초 초과 시 `RETRY_DEADLINE_S`를 30으로 낮추거나 `_generation_budget` 상한 512→384, 그래도 부족하면 AWQ(`Qwen/Qwen2.5-7B-Instruct-AWQ`)로 전환.
3. 첫 실행은 fp16 원본 15.2GB를 받아 로딩 시점에 양자화 → 1번 셀에 2~4분 추가. 부담되면 AWQ가 5.6GB만 받음.

## 2. 검색 컷오프 분석 (조사만 — **코드 미수정**)

사용자가 검색 하네스 출력표(공개 10문항, recall 9/10, P02 MISS)를 붙임. 분석만 하고 코드는 건드리지 않았다.

### 발견 1 — 붙여준 표가 현재 코드와 불일치
현재 디스크의 `_retrieve()`를 직접 호출하면:

| | 붙여준 표 | 실제 현재 코드 |
|---|---|---|
| P02 ret_k | 1 | **2** |
| P02 MISS | 통합서비스#7, 통합약관#13 | **통합약관#13 하나만** |
| 평균 k | 1.00 | **1.10** |

`MISS=` 형식으로 출력하는 스크립트가 `하네스/`에 없음 → 표를 만든 스크립트 출처 불명. (사용자에게 확인 요청한 상태.)

### 발견 2 — 컷오프가 얹힌 척도가 잘못됨 (핵심)
[`결과기_팀구현.ipynb`](결과기_팀구현.ipynb)의 `cutoff = top_score - rerank_margin`이 **RRF 점수** 위에서 동작.
RRF는 순위 역수 합이라 `rrf_k=10`에서 점수가 **고정 계단**:

| 두 채널 순위 | RRF 점수 | 1위 대비 gap |
|---|---|---|
| (1,1) | 0.18182 | 0 |
| (1,2) | 0.17424 | 0.00758 ✅ 통과 |
| (2,2) | 0.16667 | **0.01515** ❌ |
| (2,3) | 0.16026 | 0.02156 ❌ |

`margin=0.01`은 "(1,2) 이상만 통과"와 동일. **리랭커가 얼마나 확신하는지는 전혀 반영 안 됨.** 실측상 9문항의 2위 gap이 전부 0.01515 또는 0.02156(계단값) → k=1 수렴은 필연.

### 발견 3 — margin 튜닝으로 P02 못 살림
P02의 통합약관#13은 (whole#3, sub#6) → gap 0.03482. 통과시키려면 margin ≥ 0.035, 그러면 전 문항 붕괴:

```
margin=0.035  → 공개10 exact 0/10, 평균 k 3.00, 불필요 조항 18개
```

### 발견 4 — 대안 검증: 순위는 RRF, 채택은 리랭커 원점수(0~1)
리랭커 cross-encoder 원점수는 gold(min **0.9978**)와 distractor(max **0.9715**)를 완전 분리.
공개10 + 자체 함정10(`하네스/trap_questions.json`) 스윕 결과:

| 방식 | 공개10 exact | 함정10 exact | 함정10 불필요조항 |
|---|---|---|---|
| 현재 margin=0.01 | 9/10 | 7/10 | 3 |
| **원점수 tau=0.999** | **9/10** | **10/10** | **0** |

- P02는 여전히 못 잡음(#13 원점수 0.9989 → tau를 0.998로 낮춰야 잡는데 그러면 함정셋 악화).
- 대신 **함정셋 precision 7/10 → 10/10**로 개선.

### 발견 5 — 채점은 MRR이 아니라 LLM 평가 (P02를 쫓을 이유가 약함)
대회 PDF(p3, p14) 확인:
- 예선 채점 = **Gemini 3.5 Flash 평가기가 "정답 조항 + 핵심 내용" vs 팀 답변을 비교해 품질 점수**. 상위 5팀 본선 진출.
- HTTP 응답 속도·성공률 자체엔 **별도 점수 없음**(p14 명시).
- 최종 배점: 예선 결과기 30점 + 본선 발표 50점 + 익명 교차평가 20점.

→ P02 gold 3개(계정#8/통합서비스#7/통합약관#13)는 세 약관에 중복 기재된 조항. `retrieved` 목록에서 하나 빠지는 것보다 **답변에 "몇 시간" 수치가 들어가는지**가 점수를 좌우.

### 미결 제안 (사용자 결정 대기)
- **A.** 컷오프를 원점수 tau=0.999로 교체 → 함정셋 precision 개선. (코드 수정 필요, 아직 안 함)
- **B.** P02 답변에 실제로 시간 수치가 들어가는지 확인.
