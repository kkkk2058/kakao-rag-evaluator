이 세션에서 진행한 검색기·생성기 분석, 실제 채점 결과 대조, 코드 패치 이력을 정리한다.
관련 코드: [`결과기_팀구현.ipynb`](결과기_팀구현.ipynb), [`결과기_팀구현 copy.ipynb`](결과기_팀구현%20copy.ipynb)(패치 전 원본), [`결과기_제출.ipynb`](결과기_제출.ipynb)(이 세션에서 만든 제출 후보). 설계 배경은 [`리트리버_설계노트.md`](리트리버_설계노트.md) §1~13 참조.

## 1. 초기 진단 — 검색기·프롬프트 구조 파악

`결과기_팀구현.ipynb` 1번 셀(약 2100줄)과 [`리트리버_설계노트.md`](리트리버_설계노트.md) 641줄을 전체 정독. 청킹은 조(條) 단위 72개(길이 85~3482자 불균일), 검색은 BM25(문자 bigram, 조 전체+항 최고점 RRF 결합) → 리랭커(bge-reranker-v2-m3, 조 전체+최근접 항 RRF) → 컷오프 순.

### 발견 1 — 문장 선택 계층이 사문(死文)이었다
`_focus_generation_evidence`, `_select_evidence_text`, `_select_coverage_evidence` 등 약 200줄이 **정의만 있고 어디서도 호출되지 않음**. 실제 생성 경로(`_build_evidence_blocks`)는 `_prepare_article_evidence`까지만 거치고 조 전체(또는 구조 축약본)를 그대로 프롬프트에 넣고 있었다.

### 발견 2 — evidence F1 상한 실측
노트북에서 함수를 AST로 원본 그대로 추출해 로컬 재현(`rank_bm25.BM25Okapi`를 동일 공식으로 직접 구현). 공개 10문항 기준:

| | bigram F1 |
|---|---|
| 조 전체 그대로 복사 | 0.528 |
| 문장을 완벽히 골랐을 때 상한 | 0.804 |
| 실측 답변(§12-1 기록) | 7B 0.671 / 3B 0.637 |

`_focus_generation_evidence`를 사후 적용해 보니(어휘 폴백 기준) 0.528 → 0.681, **20문항(공개10+함정10) 하락 0건**.

### 발견 3 — P09 검색 실패 원인
조 전체 채널은 정답(제10조)을 1위로 맞혔는데, 항 최고점 채널이 무관한 조(제5조, "이용 중단"이라는 표면 어휘 일치)를 1위로 끌어올려 RRF 결합에서 정답이 2위로 밀림. §2-1에서 "고쳤다"고 기록된 실패가 실은 문항을 옮겨간 것으로 확인.

### 발견 4 — retrieved 70% 낭비
폴백 경로에서 `retrieved`가 항상 4개 반환되는데 실제 생성에 쓰이는 건 1~2개뿐 (`_prune_contexts_by_coverage`가 나머지를 버림). "실제 사용한 근거만 반환" 규격과 어긋남.

## 2. 1차 패치 — 문장 선택기 배선 (`결과기_팀구현.ipynb`)

- `_build_evidence_blocks`에서 `_prepare_article_evidence` 결과를 `_focus_generation_evidence`에 한 번 더 통과시키도록 연결
- 예외절(`다만/단,/단서`) 인접 보존 규칙 추가 — T02(위치정보약관 제9조, "예외 없이 즉시 파기되나요?")에서 정답 예외절이 어휘 관련도로는 최저인데 F1로는 최고인 사례를 발견하고 반영
- 20문항 검증: evidence F1 0.401→0.527(+0.126), 하락 1건(T02) → 예외절 규칙 추가 후 0.538, 하락 0건

## 3. 3B 기본 모델 전환

§12-1 A/B 실측(7B 0.671 vs 3B 0.637, 95% CI [-0.060, +0.129] — 유의하지 않음)을 근거로 `USE_7B_GENERATION` 스위치 도입. 기본 3B fp16, `True`로 바꾸면 7B-4bit 시도 후 실패 시 자동 3B 폴백. `bitsandbytes` 설치도 스위치에 종속시켜 기본 경로 실패 지점 제거. 로더 6갈래(GPU유/무 × bnb정상/없음/로딩실패)를 스텁으로 전부 검증.

## 4. `copy`/`팀구현`/`제출` 3파일 차이 규명

사용자가 세 파일의 차이를 물어 정밀 대조. `팀구현`과 `제출`은 cell0·cell1이 바이트 단위 동일(검증셀 3~5번 유무만 다름). `copy`(패치 전 원본) 대비 `팀구현`은 문장선택기 배선 + 3B 전환 두 묶음만 차이. 이후 사용자가 "코드를 바꾸고 결과가 나빠졌다"고 보고 — 원인이 문장선택기 배선(evidence 축소)과 모델 교체(7B→3B)가 동시에 일어나 귀속 불가능한 상태였음을 지적하고, `USE_7B_GENERATION=True`로 모델 변수만 격리하는 방법을 제안.

## 5. 대규모 자체 평가셋 생성 — 하드코딩·일반화 감사

사용자가 "하드코딩 여부"와 "비공개 30문항 일반화"를 물어 정적 감사 + 대규모 합성 평가를 수행.

- **정적 감사**: 공개문항 텍스트/정답 하드코딩 0건, 문항 ID(P01~P10, T01~T10)는 전부 주석·docstring 안에만 존재. 워밍업 호출이 P01 질문 문자열이지만 정답 저장 없음.
- **평가셋 생성**: 72개 조항 전체에서 자동 생성. v1(정답 문장 통째 복사, 너무 쉬움) → v2(특징어 나열, 부자연스러움) → v3(공식 10문항의 난이도 지표에 맞춰 보정: 질문↔정답 bigram 커버 0.39, 최장 연속복사 15자, 문서명 명시 30%)로 3회 반복. 최종 v3 91문항 + 쉬운 대역 286문항 = 총 397문항.
- **검색 결과**: 397문항 전체에서 **Recall@4 = 1.00, 실패 0건**(리랭커 없는 폴백 경로 하한).
- **구조적 하자 확인**: `max_length=512` 절단이 72개 중 12개(17%) 조항에 영향(최악 통합서비스약관 제12조, 2423자 유실) — §13에서 이미 지적된 미반영 사항. 보일러플레이트 제목 중복 36/72개(50%). retrieved 73% 미사용.

## 7. 패치 ① — 커버리지 재시도 과소생성 구제

P08처럼 근거가 짧은데(≤200자, ≤3문장) 답변이 그 절반도 안 담았을 때, `_cov_find_missing`의 관련도 문턱(`max(0.45, top×0.75)`)을 생략하도록 예외 추가. **문턱 없이 전면 적용은 위험**함을 397문항 시뮬레이션으로 먼저 확인(86문항 발동, 84건 악화 평균 -0.089) → 200자 상한으로 좁히자 발동 0건. 실제 제출 답변으로 재현: P08만 바뀌고 0.400→0.935, 나머지 9문항 flag 불변.

## 8. 패치 ② — 3B 모델을 제출본에 실제 적용

`결과기_제출.ipynb`(대회 규격 2셀: 결과기+공통러너)에 `max_length 512→2048` + 위 커버리지 패치 + 3B 기본 전환을 누적 적용. `copy` 대비 실코드 55줄. 사전 근거는 §12-1 기준 약 −0.7점으로 추정(P07 회복 vs P06·P09 손해가 상쇄)되나 통계적으로 미결이라 **A/B로 판단하라**고 명시.

## 9. 커버리지 검증 하네스 제작 (`하네스/cell6_커버리지_검증셀.py`)

사용자가 "커버리지가 실제로 어떻게 동작하는지" 질문 → `_cov_find_missing`/`_cov_covered_count`/`_cov_grounded` 3단 게이트 구조를 코드 그대로 설명 (탐지 → 재생성 → 단조 채택 게이트). 이어서 base(재시도 전)/cov(재시도 후) 답변을 나란히 잡아 **공백 어절 토큰 F1**으로 비교하는 검증 셀을 신규 제작. 스텁 환경(가짜 리랭커=어휘겹침 반환)에서 20문항 전량 에러 없이 실행 확인 후 전달.

### Colab 실행 결과 (1차, 헤더 버그 발견 전)
채택 8/20, 개선 4, **악화 4**(F1 순변화 +0.0246, 30점 환산 +0.74점). 악화 4건(P09, T03, T08, T10) 전부 길이 폭증+precision 급락 패턴. 단, T05도 10배 늘었지만 최대 개선(+0.559)이라 **길이만으로는 가를 수 없음**을 확인 — precision 저하는 gold 대조 없이는 추론 시점에 알 수 없어 별도 가드를 넣지 않기로 판단.

### 발견 5 — 근거 블록 헤더 오염 (신규 버그, 20/20 문항)
`_build_evidence_blocks`가 만드는 각 조 블록의 첫 줄("{문서명} 제{N}조 {제목}")이 `_split_generation_units`에서 줄바꿈 기준으로 쪼개지며 **문장 하나로 오인**되어 커버리지 후보 풀에 섞임. 실측: 20문항 전부 발생, T05·T10은 flag 슬롯 하나를 헤더가 통째로 점유. 헤더를 "빠진 핵심 문장"으로 지목하면 모델이 본문 인용 표기를 만들어내는 셈이라 §10-2 실측(F1 −0.135)과 정면 배치.

## 10. 패치 ③ — 헤더 필터 (`_COV_HEADER_RE`)

`OFFICIAL_DOCUMENT_NAMES` 기반 정규식으로 `_cov_find_missing`의 `ev_units` 구성 시 헤더 줄 제외. 로컬 재현: T05 flag 2→1(헤더 제거), 나머지 실문장 flag는 불변. 스모크 테스트 통과 후 `결과기_제출.ipynb`에 반영.

## 미해결 / 다음에 볼 것

1. **헤더 필터 반영 후 Colab 재검증 필요** — 악화 4건이 줄어드는지, T05·T10 flag 변화 확인
2. **P01~P04에서 재시도가 base와 완전 동일한 답을 냄** — `_cov_find_missing`이 문장은 정확히 지목하는데 재생성이 반영을 안 함. 재시도 프롬프트(`_build_user_prompt`의 retry_block) 쪽 문제로 추정, 아직 손대지 않음
3. **P07에서 게이트가 실제로 더 나은 답변(F1 +0.12)을 거부** — `_cov_covered_count`의 45% 문턱이 너무 타이트한 사례. 원인 파악만 하고 수정은 보류(근거 부족)
4. **`_cov_covered_count`/precision 가드 부재** — 넣을 근거(추론 시점 신호)가 없어 의도적으로 보류. gold 없이 판별 가능한 대안 신호가 나오면 재검토
5. **3B 전환의 실측 검증** — 아직 Colab에서 P06·P07·P09 문항별 결과를 못 봄. `USE_7B_GENERATION=True/False` A/B 필요
6. **`결과기_최종.ipynb`와의 정합성 확인** — 이 세션 밖에서 진행된 편집으로 보이므로, 어느 쪽을 최종 제출본으로 쓸지 결정 필요
